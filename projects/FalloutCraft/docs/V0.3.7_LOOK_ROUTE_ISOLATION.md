# FalloutCraft v0.3.7 — Fallout look-routing isolation

## What v0.3.6 proved

Minecraft 26.3 successfully completes mirror-world startup, creates the player, binds to Fallout, publishes the HUD/hand overlay, and remains alive. Fallout then freezes and its shared-memory heartbeat stops. Minecraft detects the dead host about eight seconds later and drops the link.

The eight-second delay is the heartbeat timeout; it does **not** mean Fallout remained healthy for eight seconds after the last visible frame.

v0.3.6 already changed the host movement call from `Actor::SetPosition(position, true)` to `Actor::SetPosition(position, false)`. The freeze remained, so Havok-controller warping is not the only unsafe host call.

## New finding from recovered native disassembly

Immediately after the `Actor::SetPosition` call, v0.3.4/v0.3.6 conditionally calls a second Address-Library-resolved Fallout function with the player object and a single float derived from Minecraft look state. This is the native **Fallout look-routing** path described by the plugin's own startup diagnostic.

It is executed on the same per-frame takeover path.

## v0.3.7 change

- keep Minecraft-authoritative movement;
- keep `Actor::SetPosition(position, false)` so the Fallout reference can follow without host-controller warp;
- skip the separate resolved Fallout look-routing function entirely;
- keep shared-memory IPC, input bridge, and HUD/hand overlay active.

This is an isolation test. Mouse/camera rotation may not follow Minecraft correctly in this build. The goal is to determine whether the second host mutation is the operation that stalls Fallout's update thread.

## Test gate

1. Fallout remains responsive for 30+ seconds after the Minecraft advancement/recipe startup burst.
2. FalloutCraft link stays up.
3. WASD changes Minecraft/player position.
4. HUD/hand continues updating.
5. Note whether mouse look fails or remains usable.
