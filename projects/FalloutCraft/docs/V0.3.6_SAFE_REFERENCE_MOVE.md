# FalloutCraft v0.3.6 — safe reference movement test

## Why this build exists

The v0.3.5 test reproduced the v0.3.4 failure: Minecraft completes mirror-world startup, the first overlay frame is published/presented, then Fallout stops updating the shared-memory heartbeat and Minecraft drops the link several seconds later.

The 0.3.5 throttle therefore did **not** solve the freeze.

## New native change

The recovered v0.3.4 callsite invokes Fallout's `Actor::SetPosition(const NiPoint3&, bool updateCharController)` virtual at slot 0xCA with `updateCharController=true`.

v0.3.6 changes only that boolean to **false**. Minecraft remains authoritative for movement/physics, while Fallout updates the actor reference without asking the host Havok character controller to warp every frame.

This is intentionally a stability-first test. If it stops the freeze and allows movement, the next native step is a separately validated low-rate character-controller synchronization path rather than coupling it to every actor-reference update.

## Test gate

Do not promote this build until runtime tested. The key observations are:

1. Does Fallout remain responsive after Minecraft finishes achievements/recipes?
2. Does the FalloutCraft link remain up for at least 30 seconds?
3. Does WASD move the Minecraft-authoritative player / Fallout reference?
4. Does mouse look work?
5. Does the Minecraft HUD/hand overlay remain visible?
