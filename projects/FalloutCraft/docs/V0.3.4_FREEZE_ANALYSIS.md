# FalloutCraft v0.3.4 freeze analysis

## What is confirmed working before the freeze

The Minecraft log shows that the 26.3 client starts, FalloutCraft 0.3.4 loads, the Fallout link comes up, the mirror world is created, the integrated server starts, and the local player logs in. The takeover handshake then starts, the Minecraft player is bound to the Fallout world position, overlay capture starts, and the first HUD/hand frame is published.

The FalloutCraft native log shows the first stable Minecraft state is read, the teleport acknowledgement matches, Minecraft ownership of input begins, the first `Actor::SetPosition` call returns, interpolation becomes active, the temporary GDI overlay window is created, and the first frame is presented.

Minecraft then loses the Fallout shared-memory heartbeat several seconds later. No Fabric crash is logged at the transition.

## Primary suspect

v0.3.3 reported a 20 Hz puppet movement path. v0.3.4 reports a `per-frame interpolated Actor::SetPosition puppet`. The first call returns, so the failure is not simply an invalid vtable slot on first use. The strongest current hypothesis is that repeatedly invoking Fallout's actor/Havok position path every host render frame eventually stalls Fallout's main/update thread.

## v0.3.5 safety change

Separate physical actor updates from visual interpolation:

- physical Fallout player / Havok puppet update: ~20 Hz, aligned to Minecraft physics ticks;
- camera / view / visual interpolation: every Fallout frame;
- heartbeat: updated from a path that cannot be starved by expensive puppet or compositor work;
- no synchronous raycast or collision feedback loop on the Fallout main thread until individually validated.

This keeps SkyCraft's smooth presentation model without assuming Skyrim's per-frame player relocation is safe in Fallout 4.
