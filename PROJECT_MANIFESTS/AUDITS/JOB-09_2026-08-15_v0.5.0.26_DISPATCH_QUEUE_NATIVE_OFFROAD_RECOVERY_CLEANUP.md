## Paid RLS behavior confirmed

### Native Repo
- Repo remains a singleton system centered on one module-global `repoJobInstance` and shared route/delivery state.
- A second call to the native Repo generator is therefore NOT a safe multi-Repo implementation.
- Native Repo payout is dynamic: vehicle value, route distance, Repo tier, Recovery bonus, economy/difficulty adjustment and elapsed completion time contribute to the result.
- JOB-09 must keep native Repo completion/reward/Recovery XP owned by RLS.

### Native Off-Road Recovery
- `MAX_OFFERS = 3`
- `MAX_ACTIVE_PER_MAP = 3`
- RLS already persists multiple active recovery jobs and supports selecting/tracking among them.
- Public APIs used by the adapter include state request/read, offer acceptance, recovery-yard selection/cancel, track job and abandon job.
- Native Recovery Yard selection only recognizes legitimate purchased RLS garages flagged as Recovery Yards with an RLS recovery drop-off spot.

## v0.5.0.26 changes

### 1. Repo player-facing UI cleanup
Removed implementation/debug wording such as:
- `Pay + XP owner: RLS 2.7 — no duplicate JOB-09 reward`
- `RLS reward: Calculated by RLS during the repo workflow`

The Dispatch Center now presents player-facing Repo information instead.

A source-derived `Estimated payout` is shown when enough native Repo data exists. It is explicitly an estimate because native RLS does not permanently lock the final payout at job generation and completion time can affect the final result.

Normal RedFox-authored Tow calls continue to show a fixed `Quoted job pay`, because JOB-09 does set those payouts when the call/destination is established. A yard change recalculates that quoted amount before delivery.

### 2. Persistent Dispatch Queue
Added persistent profile fields:
- `dispatchQueue`
- `nextDispatchQueueId`

New behavior:
- up to 25 queued assignments;
- requesting another job while a RedFox scene or native Repo is active can queue the work instead of producing the old global blocking warning;
- queued items persist through the normal JOB-09 save state;
- Dispatch UI can start/remove queued work when the underlying system is safe to activate;
- scheduler is prevented from blindly filling work while a native Repo is active, while manual queue requests remain allowed.

Important: a RedFox Dispatch Queue is NOT the same as multiple simultaneous native Repo instances. RLS 2.7.0.1 Repo remains singleton. Additional Repo requests may wait in the queue until the active native Repo is completed/cancelled.

### 3. Removed the global active-Repo Tow blocker
An active native Repo no longer blocks unrelated RedFox Tow/recovery requests or emits the unwanted global popup.

Only operations that would require a second simultaneous native Repo are deferred/queued.

### 4. Multi-car route-target fix
Previous behavior always favored the first undelivered accident target. If the player picked up target #2/#3 first, navigation could repeatedly yank back to target #1.

v0.5.0.26:
- detects an undelivered target that has materially departed its pickup position;
- favors the moved/in-transit target nearest the player;
- holds that target through a sticky `routeTargetVehicleId` while it is in transit;
- clears the sticky target after delivery and advances to the next remaining target.

Goal: the GPS follows the vehicle the player is actually working rather than constantly reasserting the nominal first target.

### 5. Native RLS Off-Road Recovery added to RedFox Dispatch
JOB-09 now exposes RLS Off-Road Recovery through an adapter instead of cloning it.

Dispatch can show:
- Recovery level and payout bonus;
- active recovery count out of RLS's native max of 3;
- active recovery jobs and phases;
- available native Recovery offers;
- native reward/distance information;
- Track / Abandon controls;
- native Recovery Yard chooser when RLS asks for one;
- button to open the native RLS Recovery Board.

RLS remains authoritative for native job target, lifecycle, payout, damage reduction, recovered-vehicle reward and shared `careerSkills-recovery` progression.

### 6. Multi-RedFox-yard destination selection
For RedFox-authored yard-bound recovery/tow work, the player can choose among available RedFox Tow Yards before the first delivery.

Covered RedFox paths include recovery/rollover/accident/abandoned and yard-bound impound/fallback cases.

Changing the selected yard:
- updates destination identity/storage key;
- updates routing;
- recalculates the fixed RedFox quoted pay based on the new destination distance;
- persists the active job snapshot.

Purchased native RLS Recovery Yard -> RedFox Tow Yard designation remains supported from v0.5.0.24/v0.5.0.25.

### 7. Queue-another-job controls
While a RedFox event is active, Dispatch offers queue controls for the supported Tow/recovery types and RLS Repo, so the player can build a work list without abandoning the current scene.

## Intentionally deferred to the formal business/facility phase

### Native RLS Recovery -> arbitrary RedFox-only yard
This is NOT spoofed in v0.5.0.26.

Paid RLS source only treats legitimate purchased RLS recovery facilities with `isRecoveryYard` and a valid `recoveryDropoffSpotName` as native Recovery destinations. The correct solution is to make RedFox Tow a formal RLS business/facility and give its legitimate business garage/recovery sites real facility data, rather than forging native flags on arbitrary locations.

### True simultaneous native Repo instances
Not implemented. Native RLS Repo is singleton. JOB-09 now queues additional Repo requests safely. A true multi-native-Repo compatibility layer would require a separate source-level redesign and is not part of this cleanup.

### JOB-13 FoxNet Auction
No auction lifecycle changes in v0.5.0.26. User explicitly approved pausing auction work while RLS/Tow integration is stabilized. Existing external-consignment handoff remains open for later.
