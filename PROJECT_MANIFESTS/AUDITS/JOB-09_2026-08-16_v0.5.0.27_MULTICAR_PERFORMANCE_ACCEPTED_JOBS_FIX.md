## Runtime problem reported

A JOB-09 Multi-Car Accident Cleanup produced a scene containing a semi tractor / loaded trailer composition and forklift/industrial equipment. Accepting the multi-car job also caused a long freeze. User also requested that accepted jobs remain visible so several jobs/recoveries can be accepted and selected.

## Root cause found in v0.5.0.26

The older passenger-only protection did not cover every accident source.

- Random Events crash imports had a passenger-only target filter.
- JOB-09 procedural `accidentPlans` still explicitly contained semi/trailer, heavy-truck and bus variants.
- Saved/provider accident templates could reroll/replay non-light target classes.
- Saved accident scene equipment could replay nonessential vehicle/equipment objects.

The screenshot therefore matched a real gap in the v26 filters; it was not just a bad classification message.

## v0.5.0.27 changes

### 1. Strict light Multi-Car Accident target rule

Multi-Car Accident Cleanup is now a light/passenger road-vehicle job by default.

Excluded from Multi-Car tow-target selection:

- semi tractors
- trailers
- buses
- heavy/vocational trucks
- tow/recovery equipment
- construction/industrial vehicles
- forklift/construction identifiers
- detached equipment / fork / bucket / crane-style attachment identifiers
- emergency-service vehicles as ordinary crash targets

Heavy trucks, semis and trailers remain available through their dedicated recovery job types rather than Multi-Car Cleanup.

The light rule is applied to:

- procedural accident plans
- saved accident templates
- event-library/provider templates
- Random Events Multi-Car Crash targets

The heavy/semi/bus procedural plans remain in source for compatibility/testing if the light-only setting is explicitly disabled, but they are not eligible under the default/user-requested Multi-Car mode.

### 2. Nonessential accident equipment filtering

For saved Multi-Car accident templates, non-emergency saved support/equipment vehicle objects are skipped instead of replayed. Required roadway police/emergency support is still handled by the existing safety logic.

For Random Events Multi-Car Crash imports, nonessential rows classified as equipment are removed while emergency support may remain.

This specifically prevents forklift/fork/industrial attachment objects from being carried into normal Multi-Car Cleanup as scene baggage.

### 3. Prepared light-vehicle candidate pool

v27 adds an incrementally prepared Multi-Car passenger candidate pool.

- The eligible catalog is filtered into a light crash pool over multiple frames.
- Default work is six catalog entries per frame.
- If an accident is accepted immediately after load, only limited chunks are advanced until a small usable roster is available.
- The prepared pool is then reused for multi-car target selection.

Purpose: move catalog filtering/preparation out of the single acceptance frame and avoid repeatedly rescanning the installed configuration set.

This does **not** claim to make BeamNG `core_vehicles.spawnNewVehicle()` asynchronous. A first-time model/config asset load may still hitch. The biggest expected improvement comes from no longer loading several large articulated/heavy/industrial configurations in one Multi-Car scene.

### 4. Always-visible accepted jobs summary

Dispatch now shows `MY ACCEPTED TOW / RECOVERY JOBS` even when the RedFox waiting queue is empty.

The summary includes:

- active RedFox tow/recovery job
- active native Repo
- all active native RLS Off-Road Recoveries
- waiting RedFox / Repo queue items

Active RLS recoveries can be selected/tracked from the summary.

### 5. Native RLS multi-recovery board while a RedFox call is active

The existing RLS Off-Road Recovery adapter is now also shown while a RedFox scene is active. This allows the user to accept and track RLS's native multiple recoveries without closing/finishing the RedFox dispatch first.

RLS remains authoritative for those recoveries, including its native limit of three active jobs per map.

### 6. RedFox queue architecture remains safe

This build does not convert JOB-09's singular `runtime.activeEvent` into multiple simultaneously spawned RedFox scenes. Additional RedFox / Repo requests continue to persist in the accepted/waiting queue. This avoids a risky pre-business-garage refactor of marker, save, delivery and scene-cleanup ownership.

The distinction is intentional:

- native RLS Off-Road Recovery: multiple active jobs supported now, up to 3;
- RedFox jobs / Repo requests: may all be accepted/queued and are now clearly visible, but only one RedFox scene and one native Repo instance are activated at a time.

A later multi-active RedFox scene refactor, if still desired, must be a separate source-verified project rather than hidden inside this cleanup.
