## Why this hotfix was required

David correctly reported that the application version number must be updated with every released test build, not merely the ZIP filename and GitHub audit. Previous builds had inconsistent version reporting: some package names and audit files advanced while visible or generated metadata could still report an older version. In particular, v0.2.5 visibly retained the older editor-header number, and older hard-coded `0.2.0` strings remained in generated mod reports, ZIP edit manifests and RedFox watermark metadata.

This was a release-discipline failure. A tester must be able to identify the exact running build from the application itself and from every artifact it generates.

## Implemented in v0.2.7

- Central application version updated to `0.2.7`.
- Main window title uses the centralized version constant.
- Embedded editor header now has a dedicated version element and is overwritten from the centralized `APP_VERSION` after the editor loads.
- Editor browser title is updated from the same runtime version.
- Editor-ready status message includes the current version.
- Shared bootstrap now records `app_version` together with the active application folder.
- Launcher bootstrap writes `app_version: 0.2.7`.
- Current README, changelog, guide, start file and validation report identify v0.2.7.
- Added machine-readable `build_info.json`.
- Generated BeamNG mod build reports now use the centralized current application name/version.
- Existing-ZIP edit manifests now use the centralized current application name/version.
- RedFox generated-file watermarks now use the centralized current application name/version.
- Historical validation files retain their original historical version labels rather than being falsely rewritten.
