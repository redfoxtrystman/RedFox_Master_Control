**Date:** 2026-08-05  
**Owner:** David / Captain  
**Status:** STATIC/HARNESS VERIFIED — BEAMNG RUNTIME UNPROVEN

## Runtime evidence

Screenshots from v0.4.9.4/0495 showed:

- one portal view with 22 fleet units and 8 yard records while other pages showed zero;
- a connected header while the sidebar still said `Waiting for live connection`;
- legacy WEUI and the web/GMUI company portal visible simultaneously; and
- `[object Object]` in Records & History vehicle lines.

## Root causes

1. Multiple ancestor hosts could answer the same iframe request; actions could also be received by more than one relay.
2. The bridge had regressed toward `extensions.redfoxTowRecoveryDispatch`, while the live WEUI state is on `rawget(_G, "redfoxTowRecoveryDispatch")` after loading.
3. The global Tow app bridge accepted messages from unrelated FoxNet/phone Tow iframes.
4. A generic `bridge.lua.call` adapter was treated like raw `engineLua` even though that contract was not proven.
5. Connected but incomplete responses could replace a valid complete state.
6. Several dispatch/recovery paths opened the legacy `mainWindow` directly without closing/replacing the web portal.
7. History joined vehicle objects directly.

## Repair

- One immediate owning host per iframe; nested phone/browser layers explicitly relay upward.
- Each PC/phone/Angular relay verifies `event.source` against its own iframe.
- Global table first; `extensions...` is compatibility fallback only.
- Full `redfox.tow.web.v1` contract required before a response is accepted as connected.
- Disconnected, incomplete and stale responses cannot erase valid state.
- Web portal and legacy WEUI are mutually exclusive.
- Automatic dispatch, resume and abandoned-decision opens use one preferred interface.
- History vehicle objects are rendered by name/model/config instead of `[object Object]`.
